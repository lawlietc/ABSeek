# ABSeek 信源/展示分离改造方案

> 目标：把「采集即展示」改为「采集当信源、展示单独生成」。采集回来的信源简报只作信息源引用，每天出图的实际内容由 agent 依据信源**新增独立的展示简讯**，实现展示内容可控、可聚合信源、可自由编辑。

## 一、流程对比

**当前（采集即展示）**
```
采集 → raw 简讯(md) → agent 改同一份文件(title/aspect/tags/status) → 出图
```
采集与展示共用一份实体，agent 直接改动采集回来的文件，展示语义（title 双语、aspect 等）全部压在信源上，内容质量不可控。

**新（信源 / 展示分离）**
```
采集 → 信源简报(md, 只读引用) ─┐
                              ├→ agent 聚合/筛选 → 展示简讯(md, 独立新增) → 出图
多个信源报道同一事件 ──────────┘        ↑ 展示简讯引用多个信源 → sourceCount 属性
```

## 二、数据模型

采用**分目录分离**（语义清晰、互不污染），而非用 status 区分：

```
data/profiles/{id}/
  briefs/          # 信源简报（采集写入，只读引用，不再被编辑成展示）
  stories/         # 展示简讯（agent 新增，出图唯一数据源）
```

> 注：目录已在多 Profile 方案中定型为 `data/profiles/{id}/`，这里的两层结构（`briefs/` + `stories/`）与该方案合并设计。

### 信源简报 brief
保持现有字段，但不再承担展示职责（title 存原文即可，不必双语 / aspect）。仅作信息源，供 agent 聚合与溯源。

### 展示简讯 story（新增实体）

```yaml
id: {date}-{seq}-{slug}    # 沿用现有规则；聚合产物无单一源，故不含 source 段
date: 2026-08-09
title: {zh, en}            # agent 完全自定义
summary: {zh, en}
category: ...
tags: [...]
customAttrs: {...}
status: raw → processed → reviewed → exported
sources:                   # 信源关联（主关联 briefId，附 sourceId 便于展示来源网站）
  - { briefId: "...", sourceId: "ign", sourceName: "IGN" }
  - { briefId: "...", sourceId: "arxiv", sourceName: "arXiv" }
sourceCount: 2            # 不落盘，由 sources.length 推导（模板展示「N 家媒体报道」）
body:                      # agent 自定义正文
```

### 核心收益对应
- **可控**：展示内容完全由 agent 生成，不依赖采集原文质量。
- **信源数量属性**：`sources` 列表 + `sourceCount`，一条 story 聚合多家报道，出图模板可直接展示信源数 / 来源网站。
- **编辑空间**：agent 只写 story，采集的 brief 原样保留不被动。

## 三、各模块改动点

| 模块 | 现状 | 改动 |
|---|---|---|
| 采集 `collector` / `briefRepo.saveCollected` | 写入 `briefs/`，字段含展示语义 | 写入 `briefs/`（信源），`title` 存原文，保留 `priority` 用于聚合排序 |
| 采集去重 `dedup` | 跨源对 raw 去重 | **保留**：避免同一信源重复入库（仍必要） |
| 展示去重 | 采集后 `brief dedup --auto` | **移出采集阶段**：由 agent 聚合时自然解决（同一事件 → 一条 story 多信源） |
| 出图 `autoExport` / `export` | 按 `status`+`date` 从 `briefs` 筛选 | 改为只读 `stories/`，按 story 的 status+date 筛选 |
| 数据层 | 单 `BriefRepo` | 拆 `BriefRepo`(信源) + `StoryRepo`(展示) |
| watcher / GUI | 监听 `briefs/` | 同时监听 `stories/`，前端分两列表 |
| CLI | `brief ...` | 新增 `story ...`（list/get/save）；`collect` 仍写信源；`export` 读 story |
| skill | STEP3 改 raw 简讯 | 拆两步：STEP3 读信源 → **STEP3.5 生成展示简讯**（聚合多信源、自定义文案、写 sources/sourceCount） |
| 模板 | `aspect` 绑定 | 不变；story 同样走 `default-bindings.json` |

## 四、兼容与迁移

- 旧 `briefs/` 里已 `processed` 的展示数据：**归档保留**（历史出图数据不迁移进 stories，从新模型重新积累展示简讯）。
- CLI 默认 `--profile game` 兼容不变。

## 五、与多 Profile 方案的顺序关系（关键分析）

两个改动维度不同：
- **多 Profile（A）**：基础设施重构，不改变业务模型，默认 game 向后兼容。
- **信源/展示分离（B）**：业务模型变更，改变出图数据源（briefs → stories），是行为变更。

三种顺序对比：

| 维度 | 先 A 后 B | 先 B 后 A | 合并设计 + 先 B 后 A（推荐） |
|---|---|---|---|
| 目录迁移次数 | 迁入 profile（1 次）→ B 再加 stories（第 2 次） | 平铺加 stories（1 次）→ 迁入 profile（第 2 次） | **只迁 1 次**（一次定型） |
| 行为风险 | A 阶段无行为变更（安全） | B 在平铺目录做，A 再重构目录 → 白搬家 | 目录先定型，B 不碰目录 |
| 独立可验证 | A 验证不了业务价值 | B 阶段即可验证「展示可控」 | B 先在单 profile 跑几天验证 |
| 新 profile 的模型 | 复制"采集即展示"旧模型 → **错误模型 × N** | 先定对模型再复制 | 每个新 profile 天然含两层结构 |

**核心矛盾**：A 不是纯基建——它要求"一个 profile 内部长什么样"先明确。若先做 A，复制到新 profile 的仍是旧模型，等于把 B 的返工乘以 profile 数量。故业务模型（B）必须先定。

### 推荐落地顺序

```
1. 搭骨架：data/profiles/game/briefs + stories，现有数据归档进 game/briefs
2. 信源/展示分离（B）：StoryRepo、collect→信源、export→stories、CLI story、skill 生成 story
   → 默认 game 先跑几天，验证「展示可控 + sourceCount 聚合」模型
3. 多 Profile（A）：--profile、profiles.json、rules.json、skill 参数化
   → 把已验证的 game 模型复制成 ai，天然带 briefs+stories 两层
```

**理由汇总**：
1. **目录只迁一次** —— 两个改动都动 `data/`，一次性设计成 `profiles/{id}/briefs|stories`。
2. **核心痛点先落地** —— "展示不可控"是最先要解决的问题，并单独验证。
3. **先定模型再复制** —— 避免 A 把"采集即展示"旧模型复制到多个新 profile。
4. **行为变更先在单 profile 收敛** —— B 改出图数据源是高风险行为变更，先在默认 game 跑稳再推广。
5. **A 建立在已验证的正确模型上** —— 每个新 profile 直接获得正确的两层结构。

> 唯一反对项（先 A 后 B）在本方案被化解：A 的骨架（目录定型）已在第 1 步完成，A 的剩余部分（--profile / 规则 / skill 参数化）不依赖 B 的目录，不存在"白改"问题。此方案同时拿到合并的低迁移成本与先 B 后 A 的正确性。

## 六、交付阶段

- **步骤 1：搭骨架** —— 建 `data/profiles/game/`（含 `briefs/` + `stories/`），现有数据归档进 `game/briefs`。
- **步骤 2：信源/展示分离（B）** —— StoryRepo、collect→信源、export→stories、CLI `story` 命令、skill 生成展示简讯步骤。
- **步骤 2 验证** —— 默认 game 跑几天真实数据，确认：出图只吃 stories、briefs 不再进图、`sources`/`sourceCount` 聚合符合预期、story 编辑自由度足够。
- **步骤 3：多 Profile（A）** —— `--profile`、profiles.json、rules.json、skill 参数化，把 game 复制成 ai。

## 七、已定决策

1. **`sourceCount` 不落盘**，由 `sources.length` 运行时推导（避免数量与列表不一致的腐化风险）。仅当未来出现「聚合数 ≠ 信源条目数」的综述性场景时，再引入独立字段。
2. **story 沿用 `{date}-{seq}-{slug}` 规则，`seq` 在 stories 目录下独立计数**（与 briefs 隔离，避免序号冲突）。**去掉 source 段**——story 是聚合多信源产物，无单一源可挂，来源由 `sources` 列表表达。
